Both `--acc-stride 8` and the full run now print `RESULT: PASS` (zero mismatches vs `fixtures/mock_big_ideas/gold.csv`, idempotent rerun). Bugs found and fixed:
  1. `databricks/streaming/run_demo.py` (`ensure_tables`): DDL was split on literal `;`, but `ddl_gold.sql`'s header comment itself contains a semicolon, splitting the DDL mid-comment and leaving a dangling, syntax-error statement. Fixed by stripping whole-line `-- ...` comments before splitting.
  2. `databricks/streaming/batch.py` (new `localize_utc_columns`/`localize_utc_scalar`, used in `silver_stream.py`/`gold_stream.py`): `toPandas()` returns NAIVE timestamps; feeding those straight into `minute_features`/`add_baselines`/`build_gold` (which always produce tz-AWARE UTC) crashed every comparison. **Matters for live streaming**: every `foreachBatch` call crosses this exact pandas/Spark boundary on every micro-batch, so this wasn't a one-off -- it would have broken the very first batch of any real run.
  3. `databricks/streaming/gold_stream.py` (`--history-hours` cutoff query): computed the cutoff from the WHOLE Silver table, not filtered by `run_id`/`participant_id` -- would have pulled the wrong cutoff on a shared table with multiple runs, a guaranteed condition on Databricks (one Bronze/Silver/Gold table serves every run).
  4. `databricks/streaming/merge.py`: `DeltaTable.forName` raised a `ParseException` on a 3-part `catalog.schema.table` name (`spark_catalog.smoke.*`) -- it resolves names via Spark's legacy 2-part `TableIdentifier`, not full multipart catalog resolution, even though `spark.sql`/`spark.read.table` handle the same name fine. Rewrote `merge_into`/`merge_update_only` as plain SQL `MERGE INTO` via a temp view, which is both the fix and the more portable choice (identical syntax on Unity Catalog).
  5. `databricks/streaming/merge.py` (`to_spark_df`): three more `createDataFrame` incompatibilities once an explicit schema was added (needed because an all-NULL column, e.g. Silver's baseline columns before the baseline pass runs, defeats Spark's type inference): (a) `pandas.Timestamp`, despite being a `datetime.datetime` subclass, fails Spark's exact-type check under Arrow-disabled row conversion -- fixed with `.to_pydatetime()`; (b) a nullable int column (`estimated_rest_minutes`) is `float64` in pandas, so a present value arrives as Python `float` and `IntegerType` rejects it; (c) the first fix attempt used `Series.map`, which pandas silently re-infers back to `float64`/`NaN`, undoing the whole fix -- `batch.safe_object_map` (list-comprehension + explicit `dtype=object`) is the one that actually sticks. **Matters for live streaming**: without this, no Silver or Gold row with ANY null field (every warm-up window, every gap) could ever be written.
  6. `databricks/streaming/gold_stream.py` (`start`): `gold_stream` reads Silver as a streaming source, but `silver_stream`'s baseline pass legitimately UPDATEs existing Silver rows -- Delta rejects update/delete commits in a streaming source by default (`DELTA_SOURCE_TABLE_IGNORE_CHANGES`). Added `.option("skipChangeCommits", "true")`: correct here (not a workaround) because this stream's `foreachBatch` always reloads ALL Silver fresh via `spark.read.table`, so the readStream's diff is only ever used as a "something changed" trigger signal, never read for its own row content.
  7. **The big one** -- `databricks/streaming/batch.py` (`localize_utc_scalar`'s docstring) + every `.collect()[0]["m"]`-style timestamp read in `silver_stream.py`/`gold_stream.py`/`run_demo.py`: against local Spark with Arrow disabled, `Row.collect()` silently applies the DRIVER'S LOCAL SYSTEM TIMEZONE to `TimestampType` values despite `spark.sql.session.timeZone=UTC`, while `.toPandas()` on the identical query is correct. Verified with a 3-line repro. Moved every timestamp scalar extraction from `.collect()` to `.toPandas()`.
  8. **Also big** -- `scripts/local_spark_smoke.py` (Bronze ingestion): stripped tz info (`.dt.tz_localize(None)`) before building records for `createDataFrame`. A NAIVE python `datetime.datetime` fed into `createDataFrame`'s `TimestampType`, with Arrow disabled, is interpreted using the driver's LOCAL SYSTEM timezone, not the session timezone -- verified directly (a naive `2026-10-09T16:00:00` round-tripped as `20:00:00 UTC`, exactly the EDT offset). This alone shifted every Bronze timestamp by 4 hours and was the root cause of the catastrophic (4,078/5,037-row) `estimated_rest_minutes` mismatch, since the rest-estimation algorithm is extremely sensitive to a few corrupted inputs cascading through "longest still run" detection. Fixed by keeping `event_time` tz-AWARE through to `createDataFrame`. **Matters for live streaming**: any future code (ingestion job, backfill script, test harness) that builds Bronze/Silver/Gold rows from naive Python datetimes instead of tz-aware ones will hit this silently, with no error -- just wrong data.
  9. `databricks/streaming/silver_stream.py` (lookback window): the first fix (#2-adjacent, lookback = `lag_minutes + acc_lookback_seconds`) was still 1 minute short. The earliest PENDING window's own `window_START` can be `lag_minutes + 1 full window` before the previous batch's max event time (not just `lag_minutes`), since the cutoff check is on `window_END` and a window is 1 minute long. Under-covering by exactly 1 minute showed up as PARTIAL (not zero) Silver coverage for one boundary minute per chunk transition -- silent, non-crashing, and easy to miss without a numeric diff against the pandas baseline. Fixed: `lookback_start = min_t - (lag_minutes + 1) minutes - acc_lookback_seconds`.
